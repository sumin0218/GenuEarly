# 배지 단계에 sonar 를 넣으면 어떻게 되는가

| | |
| --- | --- |
| 측정 날짜 | 2026-11-03 |
| Jev 모델 | `jev-1.13.0` (요청 기준. 응답의 `model` 은 게이트웨이가 `jev-latest` 로 정규화한다) |
| 검색 모델 | `sonar-pro` |
| 질문 세트 | `judgment-items.json` v1.6.0 — `unverifiable_claim` 의 두 질문, `record_entailment` |
| 표본 | [수동 테스트 기사](../fixtures/manual-news/) 과장 제목 10건 × 앞 3문장 = **30문장** |
| 가중치·임계값 | 건드리지 않았다. `ITEM_CAUTION_AT = 0.65` |
| 무엇을 바꿔서 쟀나 | 문장마다 **sonar 로 주변 기록을 찾아 Jev 에게 주는 길**을 더해 지금과 견줬다 |
| 스크립트 | [../experiments/badge-with-search/run.mjs](../experiments/badge-with-search/run.mjs) |

## 왜 쟀나

"배지 단계에서 sonar 가 주변 정보를 주면 Jev 가 문장별 점수를 더 확실하게 내지 않겠나"
라는 물음이 나왔다. 그러면 코드·gpt 로 따로 대목을 찾을 필요도 없고 모델 사이의 결과
차이도 사라진다. **정확도가 오르는지, 시간이 얼마나 느는지**를 실제로 불러서 쟀다.

## 대조군

과장 제목 15건 가운데 `subtype` 이 갈려 있는 10건을 썼다.

| `subtype` | 건수 | 무엇 |
| --- | --- | --- |
| `true` | 5 | **공식 출처를 확인해 요약한 과거 기록** (한강 노벨상, 봉준호 오스카 등) |
| `false` | 5 | **지어낸 사건** (손흥민 이름의 도서관, 삼성·LG 제휴 등) |

sonar 가 배지에 쓸모가 있다면 앞의 다섯에서는 기록을 찾고 뒤의 다섯에서는 못 찾아야 한다.

> **정답 라벨이 아니다.** 5건씩이라 한 건이 20%p 를 움직인다
> ([../data/README.md](../data/README.md) 1절). 방향을 보는 정도로 읽는다.

## 두 길

| | 무엇을 하나 |
| --- | --- |
| **A (지금)** | 문장 → Jev 두 질문(`factual_assertion`, `named_basis`) → `P(a)×(1−P(b))` |
| **B (sonar 추가)** | 문장 → sonar 로 기록 검색(최대 3건) → 기록마다 Jev `record_entailment` |

## 결과

### 가르는 힘 — B 가 압도한다

| | `true` 5건 (15문장) | `false` 5건 (15문장) |
| --- | --- | --- |
| **A** 점수 평균 | 0.419 | 0.342 |
| **A** 점수 중앙값 | 0.412 | 0.242 |
| **A** 0.65 이상 문장 | **3/15** | **3/15** |
| **B** 뒷받침 기록 1건 이상 | **14/15** | **2/15** |
| **B** 어긋나는 기록 1건 이상 | 0/15 | 4/15 |
| **B** 기록을 하나도 못 찾음 | 0문장 | 4문장 |

**A 는 둘을 전혀 가르지 못한다.** 0.65 이상이 양쪽 다 3/15 로 같고, 점수 범위도
`true` 0.03~0.93, `false` 0.03~0.86 으로 겹친다. 당연하다 — A 가 재는 것은
"**이 문장이 단정하면서 문장 안에 근거를 안 댔나**" 이지 "사실인가" 가 아니다.

**B 는 거의 완벽하게 가른다.** 14/15 대 2/15 다.

### 그런데 B 가 재는 것은 사실 확인이다

이 결과는 sonar 가 "Jev 를 더 똑똑하게 만든 것" 이 아니다. **질문이 바뀐 것**이다.

- A: 글이 어떻게 쓰였나 (신호)
- B: 바깥에 뒷받침 기록이 있나 (**사실 확인**)

B 를 배지에 넣으면 배지는 "주의가 필요한 신호" 가 아니라 "이 기사는 사실이다/아니다"
가 된다. [product.md](../../docs/product.md) 2절의 **"진위를 단정하지 않는다"** 와
정면으로 부딪친다.

틀리기도 한다. 허구 기사 `c-014`·`c-015` 에서 각각 **"뒷받침됨" 이 1건씩** 나왔다
(2/15). 지어낸 사건인데 sonar 가 비슷한 다른 기록을 가져왔고 Jev 가 뒷받침으로 읽었다.

### 시간 — 11배

| | 문장당 평균 |
| --- | --- |
| A | **553 ms** |
| B | **6,102 ms** (그중 검색만 4,704 ms) |

문장 15개짜리 기사로 환산하면 이렇다.

| | 기사 하나 |
| --- | --- |
| A (지금, 병렬) | 몇 초 |
| B (문장마다 검색) | **90초 이상** |

### 비용 — 130배

**30문장을 재는 데 321.97 크레딧**을 썼다 (실험 전 158.807 → 후 480.778).
문장 하나당 약 **10.7 크레딧**이다. Jev 호출 하나가 약 0.081 이므로
**sonar 검색 한 번이 Jev 130번 값**이다.

| | 기사 하나 (15문장) | 월 4,000 크레딧으로 |
| --- | --- | --- |
| A | 약 1.4 크레딧 | 약 2,800건 |
| B | 약 160 크레딧 | **약 25건** |

## 결론

**넣지 않는다.** 가르는 힘은 분명히 오르지만 셋이 모두 막는다.

1. **속도** — 11배. 배지가 몇 초가 아니라 분 단위가 된다. Jev 를 쓰는 이유 자체가 속도다
2. **비용** — 130배. 월 할당으로 기사 25건이면 끝난다
3. **성격** — 사실 확인이 된다. 하지 않기로 한 것이다

**지금 자리가 맞다.** sonar 는 리포트에 둔다 — 사용자가 버튼을 눌러, 한 기사에,
기다릴 각오로 쓰는 기능이다. 거기서는 느리고 비싼 것이 문제가 되지 않는다.

## 여기서 얻은 것

이 측정이 **다른 결정 하나를 뒷받침한다.** A 가 문장마다 점수를 내고 있고 그 점수는
이미 배지를 만들 때 받아 둔 것이다. 형광펜이 "어느 문장이 걸렸나" 를 gpt 에게 다시
묻고 있는데, **그럴 필요가 없다** — 추가 호출 없이 A 의 문장 점수를 그대로 쓰면 된다.
모델 사이의 결과 차이도 그래야 사라진다 (GE-56 후속).

## 쓰지 않기로 한 것

- **"sonar 를 넣으면 정확도가 N%p 오른다"** 로 적지 않는다. 표본이 5건씩이고,
  A 와 B 는 **서로 다른 것을 재는** 지표라 한 축에 놓고 뺄 수 없다.
- 이 수치를 정식 평가 세트 결과로 쓰지 않는다. 수동 테스트 자료는 정식 세트가 아니다.
