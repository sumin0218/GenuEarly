- 사용자에게 보이는 **문구 자체**는 여기서 정하지 않는다. [../packages/content](../packages/content/)의 몫이다. 여기는 **언제 무엇이 보이는가**만 정한다

## 2. 배지 상태

**배지는 항상 이 중 하나다.** 상태가 없는 순간은 없다 — 페이지에 붙는 순간부터 무언가를 보여 준다.

| 상태 | 언제 | 사용자에게 |
| --- | --- | --- |
| `PENDING` | 판단 요청을 보냈고 기다리는 중 | 판단 중임을 알리는 표시 |
| `SAFE` 🟢 | 점수 낮음 + 확신도 충분 | 안심 |
| `CHECK` 🟡 | 점수 중간, 또는 확신도 애매 | 확인 권장 |
| `CAUTION` 🔴 | 점수 높음 + 확신도 충분 | 주의 |
| `UNDETERMINED` ⚪ | 아래 "판단 보류가 되는 경우" 전부 | 판단하지 않음 |

**상태 이름은 코드가 쓰는 값이다.** 화면에 보이는 말은 [../packages/content](../packages/content/)에서 고른다.

### 판단 보류(⚪)가 되는 경우

⚪는 **실패가 아니라 결과다.** 사용자에게 오류처럼 보이면 안 된다.

| 원인 | 비고 |
| --- | --- |
| 확신도가 임계값 아래 | 가장 흔한 경우. 모델이 모르겠다고 말한 것 |
| 응답이 정한 보기 밖의 값 | |
| Jev 호출 실패 (429, 5xx) | 재시도 후에도 실패했을 때 |
| 타임아웃 | |
| 네트워크 끊김 | |
| 본문 추출 실패 | 아래 3-2 |
| 본문이 너무 짧음 | 일부 항목만 ⚪. [judgment-items.json](../packages/shared/judgment-items.json)의 `min_body_chars` |

**[정함] ⚪ 안에서 이유를 구분해 보여 주지 않는다.** 사용자에게 "429를 받았습니다"는 아무 의미가 없다.
다만 **로그에는 남긴다.** 우리가 고쳐야 할 것(네트워크·타임아웃)과 모델이 모르는 것(확신도 낮음)은 완전히 다른 문제다.

**[정함]** ⚪ 상태에서도 **상세를 열 수 있다.** 어느 항목이 판단됐고 어느 항목이 보류인지 보여 준다.
전부 보류면 그렇게 적는다.

### 2-1. 어디에 보여 주는가

같은 상태를 네 자리에서 보여 준다. **자리마다 근거의 세기가 달라서 생김새도 달라야 한다.**

| 자리 | 무엇을 | 근거 | 권한 |
| --- | --- | --- | --- |
| **기사 위 배지** (페이지 안) | ① 의 결과 | 제목 + 본문 + 문장 | `host_permissions` |
| **확장 아이콘 배지** | 지금 탭의 상태 하나 | 위와 같음 | **없음** (`action` 키만) |
| **팝업** (아이콘 클릭) | 상세 · ③ 결과 · ⑤ 피드백 | 위와 같음 | **없음** |
| **목록 동그라미** | ② 의 결과 | 제목만, 또는 캐시가 있으면 본문까지 (4-2) | `host_permissions` |

**[정함] ① 의 배지는 페이지 안에 둔다.** 아이콘 배지로 대신하지 않는다.
제품의 전제가 **"읽는 순간에 알려 준다"** 인데([product.md](product.md) 1절), 아이콘 배지만 있으면
사용자가 **아이콘을 쳐다봐야** 알게 된다. 기사 위에 뜨는 것이 핵심 경험이다.

#### 확장 아이콘 배지

`chrome.action.setBadgeText` 와 `setBadgeBackgroundColor` 를 쓴다. **권한이 필요 없다** — `action` 키만 선언한다.

- **탭마다 따로 둔다** (`tabId` 를 넘긴다). 다른 탭의 기사 상태가 섞이면 안 된다
- 조용한 알림이다. OS 알림(`chrome.notifications`)을 **쓰지 않는다** — 권한이 늘고,
  윈도우에서는 알림 센터로 들어가 놓치기 쉬우며, 기사를 읽는 흐름에서 벗어난다

> **TODO**: 배지에 넣을 글자. 색만으로는 색각 이상에서 구분되지 않으므로 글자가 필요하다.
> `PENDING` 을 어떻게 표시할지도 함께 정한다.

#### 팝업

`action.default_popup` 으로 연다. **권한이 필요 없다.**

| 담는 것 | |
| --- | --- |
| 지금 탭 기사의 **상세** | 어느 항목이 판단됐고 어느 항목이 ⚪ 인지. 2절 끝의 "상세를 열 수 있다" 가 여기다 |
| **③ 선택 글 검사 결과** | 5절 |
| **⑤ 오판 피드백** | 7절 |

**팝업은 우리 문서라 기사 페이지의 CSS 와 싸우지 않는다.** 임의의 사이트에 UI 를 주입하는 것보다
안정적이고, 그래서 ③ 의 결과 자리를 여기로 옮겼다 (5-1).

## 3. ① 기사 자동 검사


기사 페이지를 열면 배지가 뜬다. **제품의 중심 기능이다.**

### 3-1. 흐름

```text
기사 페이지 열림
   │
   ├─ 대상 페이지인가?            아니오 → 아무것도 하지 않는다
   │   (match-patterns.ts)
   ▼
캐시 확인                        있음 → 바로 결과 표시 (PENDING 생략)
   │
   ▼
본문 추출                        실패 → ⚪ (3-2)
   │
   ▼
배지를 PENDING 으로 띄운다       ← 여기서 이미 화면에 보인다
   │
   ▼
중계 서버에 판단 요청
   │  (요청 그룹별로 나뉨)
   ▼
응답 → 점수 합산 → 단계 결정      실패·타임아웃 → ⚪
   │  (packages/shared)
   ▼
배지를 결과 상태로 바꾼다 → 캐시에 저장
```

**핵심은 "배지를 먼저 띄우고 나중에 바꾼다"는 점이다.** 판단이 끝난 뒤에 띄우면 화면이 늦게 밀린다.

### 3-2. 본문 추출

**[정함] 사이트별 선택자를 쓴다.**

대상이 네이버·다음 둘뿐이라 범용 휴리스틱보다 정확하다. 사이트가 구조를 바꾸면 깨지는데,
**깨지면 ⚪가 뜨고 그건 우리가 의도한 동작이다.** 틀린 판단을 내놓는 것보다 낫다.

- 추출 대상은 **제목과 본문**이다. 광고·추천 기사·댓글·내비게이션은 **보내기 전에 걷어낸다** ([jev.md](jev.md) 3절 ⑤)
- **추출에 실패하면 ⚪다.** 추측해서 페이지 전체를 보내지 않는다. 관계없는 내용이 섞이면 판단이 나빠진다
- 선택자는 한곳에 모은다. 사이트가 바뀌면 거기만 고친다

> **TODO**: 네이버·다음 기사 페이지의 제목·본문 선택자를 조사해 적는다.

### 3-3. 배지 위치

**[정함] 화면 우하단 고정.**

- 기사 본문을 가리지 않고, 스크롤해도 따라온다
- **제목 옆 삽입을 기각한 이유는 "제목 위치가 사이트마다 달라 깨지기 쉽다"는 것이다.** 우리 규칙("우리 요소를 더할 뿐")과 부딪혀서가 아니다 — 그 규칙은 요소를 더하는 것을 허용하고, 실제로 ②(4-2)는 목록의 제목마다 표시를 넣는다
- **Shadow DOM 안에 둔다** (`mode: 'closed'`). 페이지 CSS와 서로 간섭하지 않게 한다

### 3-4. 상세

배지를 누르면 열린다. 다시 누르면 닫힌다.

- **보여 주는 것**: 걸린 판단 항목과 그 설명. 항목 이름이 아니라 [../packages/content](../packages/content/)의 문구로
- **보여 주지 않는 것**: **점수 숫자.** 정밀해 보이는 숫자는 단정으로 읽힌다 ([product.md](product.md) 6절)

**[정함] 근거 문장 인용은 v1.1.0으로 미룬다.**

기사 속 문장을 Jev에게 고르게 해서(Choice) 보여 주면 설득력이 크게 오른다. 생성이 아니라 선택이라
지어낼 수도 없다. 다만 **판단 항목이 하나 늘고 호출이 늘며 [judgment-items.json](../packages/shared/judgment-items.json)을
다시 열어야 한다.** 그 스키마는 이미 확정됐고, 지금 다시 여는 비용이 크다.
v1.0.0은 항목별 설명문만 보여 준다.

### 3-5. 닫기와 다시 보기

- **[정함]** 사용자가 배지를 닫을 수 있다. 기사를 읽는 데 방해가 되면 안 된다
- **[정함] 닫기는 그 페이지에서만 유효하다.** 새로고침하면 다시 뜬다
  - 기억하려면 저장이 필요하고, "어느 범위로 기억하는가"를 또 정해야 한다. 가장 단순한 쪽을 고른다

### 3-6. 같은 기사를 다시 열면

- **[정함] 캐시한다.** 같은 기사를 다시 열 때마다 호출하면 레이트 리밋과 비용이 늘고 응답도 느리다
- **[정함] 캐시는 판단 항목 단위로 쌓는다.** 기사 단위가 아니다

  ②는 제목만 보는 항목(`clickbait_headline`, `spread_inducement`)만 판단한다. 이걸 기사 단위로
  캐시하면, 사용자가 목록에서 그 기사를 눌렀을 때 **"캐시 있음"으로 보고 출처·제목-본문 일치·문장
  판단을 건너뛴 채 제목만 본 결과가 6시간 동안 기사 배지로 나온다.**

  그래서 이렇게 한다.
  - 캐시 값에 **항목별 결과**를 담는다
  - ①은 **없는 항목만** 요청한다. ②가 채워 둔 항목은 재사용한다
  - **①에 필요한 항목이 모두 채워졌을 때만** "캐시 있음"으로 본다
- 캐시에 **기사 본문을 넣지 않는다.** 판단 결과까지다 ([security/secure-coding.md](security/secure-coding.md) 6절)
- **[정함] 유효 기간 6시간.** 기사는 수정된다. 하루를 넘기면 수정된 기사를 옛 판단으로 보여 줄 위험이 커지고,
  1시간은 짧아 캐시가 거의 안 먹는다. **근거가 약한 값이라 실제 사용을 보고 조정한다**
- 캐시된 결과를 쓸 때는 **PENDING을 거치지 않고 바로 결과를 보여 준다**
- 키 형태와 URL 정규화는 [architecture.md](architecture.md) 6절에 있다

## 4. ② 포털 목록 일괄 검사

네이버·다음 뉴스 목록에서 **제목만** 판단해 낚시성 제목을 표시한다.

### 4-1. 점진 표시

**[정함] 목록 전체를 한 번에 치지 않는다.**

- **화면에 보이는 항목부터** 순서대로 판단한다
- 사용자가 스크롤해 내려가면 **그때 그 항목을 판단한다**
- 사용자는 위에서부터 채워지는 것을 본다

### 4-4. 진한 동그라미를 채우는 두 가지 길

**[정함] 캐시에 있으면 그대로 쓴다. 비용 0.**

사용자가 전에 읽었거나 ①이 이미 판단한 기사는 **본문까지 본 결과가 저장돼 있다.** 꺼내 쓰면 된다.
호출이 한 건도 들지 않으므로 안 할 이유가 없다.

**[정함] 제목에 마우스를 올려 머물면 그 기사 하나만 미리 판단한다.**

호버는 **"이걸 읽을까"** 라는 신호다. 관심을 보인 것만 쓰므로 낭비가 없고,
클릭했을 때 **결과가 이미 있어서 배지가 즉시 뜬다.**

- 기사 하나가 평균 **22건**(실측 표본 10건, 9~39문장)이라 분당 다섯 개까지 여유롭다
- 호버가 풀리면 **보내기 전이면 취소한다**
- 이미 캐시에 있으면 보내지 않는다

| 30개 | 654건 | 5.5분 |

| --- | --- |
| 주소창에서 복사 | ❌ 주소창은 페이지 밖이라 content script 에 이벤트가 오지 않는다 |

## 8. 전역 규칙

### 8-1. 레이트 리밋 — 실측으로 모양이 바뀌었다

**한도는 분 단위 예산이지 초당 속도 제한이 아니다.** 2026-10-21 에 직접 재서 확인했다.
그 전까지 이 절은 "60초에 120건"을 "초당 2건"으로 옮겨 적고 그 위에 계산을 쌓고 있었는데, **그 환산이 틀렸다.**

#### 실측 (2026-10-21, ChatKHU Gateway)

| 보낸 방식 | 결과 | 벽시계 |
| --- | --- | --- |
| 20건 **동시** | 200 × 20 | **0.66초** |
| 110건 동시 (같은 분에 26건을 이미 쓴 뒤) | 200 × 94, **429 × 16** | 1.17초 |

- 94 + 26 = **정확히 120.** 분 예산을 다 쓸 때까지는 동시 발사를 막지 않는다
- 429 에 **`retry-after: 19`** 와 `rate_limit_exceeded - Rate limit exceeded: 120 requests per minute. Limit resets at …` 이 온다. 남은 창 시간이다
- 버스트에서 응답이 느려지긴 한다 — 20건 동시 중앙 532ms, 110건 동시 중앙 914ms. 그래도 1초 안이다

#### 그래서 진짜 제약은 무엇인가

**지연은 문제가 아니다.** 기사 하나(요청 20건)가 **0.66초**에 끝난다.

**문제는 처리량 천장 하나다.** 분당 120건을 키 하나로 모든 사용자가 나눠 쓴다.

**기사당 요청 수는 `2 + 문장 수` 라 기사 길이에 그대로 비례한다.** 고정값이 아니다.
아래는 GE-32 가 모은 기사 10건의 실제 문장 수로 계산한 것이다.

| 기사 길이 | 문장 수 | 요청 | 전체 합쳐 분당 |
| --- | --- | --- | --- |
| 짧음 (단신) | 9 | 11 | **약 11건** |
| 보통 | 14~23 | 16~25 | 5~8건 |
| 긺 (기획·분석) | 28~39 | 30~41 | **3~4건** |

**전체 합쳐 분당 기사 3~11건.** 아래 계산은 중앙값에 가까운 18문장(20건) 기준이다.

| 상황 | 버티나 |
| --- | --- |
| 심사위원이 혼자 기사 몇 개를 연다 | **버틴다.** 기사당 0.66초 |
| 전시장에서 열 명이 1분 안에 기사 하나씩 연다 | **아슬아슬하다.** 10 × 20 = 200건 > 120 |
| ② 포털 목록 (제목만, 기사당 1건) | **여유 있다.** 목록 30개 = 30건 |

기사당 요청 20건 중 **18건이 `unverifiable_claim` 의 문장 단위 호출이다.** 천장을 만드는 것은 이 항목 하나다.

#### 줄일 수 있는 것

| 방법 | 효과 | 한계 | v1.0.0 |
| --- | --- | --- | --- |
| **문장을 묶어 한 요청에** | 판단 범위를 줄이지 않고 요청이 1/4로 | **쓸 수 없다. 측정해서 막혔다** (아래) | **불가** |
| **문장 수 상한** (앞쪽 N문장만) | 기사당 건수가 예측 가능해진다. N=8 이면 10건 → 분당 12건 | 뒤쪽 문장의 주장을 놓친다 | **안 쓴다** (아래) |
| **캐시** (8절) | 같은 기사를 다시 열 때 0건 | 처음 여는 기사에는 도움이 안 된다 | 쓴다 |
| **중계 서버가 429 를 받으면 ⚪** | 천장을 넘어도 화면이 깨지지 않는다 | 판단을 못 한 것은 그대로다 | 쓴다 (GE-18) |

**문장 묶기는 재 봤고 안 됐다 (2026-10-21, GE-32).** 판단 범위를 하나도 줄이지 않고 요청만 줄이는
유일한 방법이어서 먼저 시도했다. `state` 에 `s1`…`sN` 을 넣고 질문이 자기 필드를 이름으로 가리키게 하면
한 요청에 최대 16문장까지 들어간다(API 상한: 요청당 질문 32개). 그런데 **가장 작은 묶음(4문장)에서도
예/아니오가 8% 뒤집혔고 그 절반이 확신 구간에서 바뀌었다.** 묶음 크기의 문제가 아니라 다른 문장을
같은 요청에 넣는 것 자체의 문제다. 기사 10건·문장 191개·요청 927건으로 잰 결과와 판정 기준이
[../eval/experiments/sentence-batching/README.md](../eval/experiments/sentence-batching/README.md) 에 있다.

**그래서 기사당 요청은 `2 + 문장 수` 로 고정이고, 천장을 줄일 방법이 남아 있지 않다.**

**지연 때문에 2단계 표시를 할 이유는 없어졌다.** 0.66초면 기다렸다가 한 번에 띄워도 된다.
(배지를 먼저 띄우는 것은 성능 때문이 아니라 호출 실패·타임아웃 때문이므로 그대로 둔다)

#### 결정 (2026-10-21) — 정확도를 고르고 처리량을 미뤘다

이용 조건을 확인했고([jev.md](jev.md) 6-1절), **분당 120건은 고정이다. 올려 달라고 할 수 없다.**

- **[정함] ChatKHU Gateway 로 간다.** v1.0.0 에서 TypeSafe 직접 계약을 하지 않는다. 지연이 문제가 아니었고, 이용 조건이 대회 결과물 단계에서 허용이다
- **[정함] `unverifiable_claim` 의 문장 수를 줄이지 않는다.** 천장을 낮추는 가장 싼 방법이지만 쓰지 않는다.
  **먼저 넘어야 할 것은 심사이고 심사는 정확도로 넘는다.** 문장을 잘라 내면 뒤쪽 문장의 주장을 놓친다.
  처리량을 위해 판단 범위를 깎는 것은 순서가 틀렸다
- **[미룸] 부스 전시의 동시 접속.** 지우지 않고 미룬다. 아래 조건에서 다시 연다

#### 미룬 위험 — 심사에서도 닿을 수 있다

"심사위원 혼자면 여유롭다"는 **반만 맞다.** 분당 기사 6건이므로

| 심사위원이 기사를 | 분당 요청 | 닿나 |
| --- | --- | --- |
| 읽으면서 넘긴다 (30초에 하나) | 40건 | 여유 |
| 훑으며 빠르게 넘긴다 (10초에 하나) | 120건 | **경계** |
| 같은 기사를 다시 연다 | 0건 (캐시) | — |

**그래서 429 처리는 미룰 수 없다.** 문장 수를 줄이지 않기로 한 만큼 더 그렇다.
중계 서버는 `429` 를 받으면 `retry-after` 를 지키거나 그 항목을 ⚪로 돌린다 (GE-18).
화면이 깨지는 것과 "모른다고 말하는 것"은 다르다.

#### 다시 여는 조건

| 이런 일이 생기면 | 할 것 |
| --- | --- |
| 부스 전시가 확정된다 | 문장 수 상한을 eval 로 정하거나 TypeSafe 직접 |
| 심사·시연 중 `429` 가 실제로 관측된다 | 같음 |
| **대회 이후 일반 배포를 결정한다** | **이용 조건이 "대회 결과물 단계"까지다. 반드시 다시 확인한다** |

### 성능

- **[정함] 배지는 먼저 뜨고 나중에 바뀐다.** 판단을 기다렸다가 띄우지 않는다
- **[정함] 판단 요청은 페이지가 열리자마자 보낸다.** 스크롤이나 체류 시간을 기다리지 않는다
