# 기능 요구사항

**화면에서 무엇이 어떻게 보이고 움직이는가.** 구현하기 전에 여기서 정한다.

- *무엇을 왜 만드는가*는 [product.md](product.md)에 있다. 이 문서는 그 다음 층이다
- *무엇을 판단하는가*는 [../packages/shared/judgment-items.json](../packages/shared/judgment-items.json)이 원본이다
- 사용자에게 보이는 **문구 자체**는 여기서 정하지 않는다. [../packages/content](../packages/content/)의 몫이다. 여기는 **언제 무엇이 보이는가**만 정한다

> 표기: **[정함]** 결정된 것 · **[골라야 함]** 선택지를 제시했고 팀이 정한다 · **TODO** 아직 모르는 것

## 2. 배지 상태

**배지는 항상 이 중 하나다.** 상태가 없는 순간은 없다 — 페이지에 붙는 순간부터 무언가를 보여 준다.

| 상태 | 언제 | 사용자에게 |
| --- | --- | --- |
| `PENDING` | 판단 요청을 보냈고 기다리는 중 | 판단 중임을 알리는 표시 |
| `SAFE` 🟢 | 점수 낮음 + 확신도 충분 | 안심 |
| `CHECK` 🟡 | 점수 중간, 또는 확신도 애매 | 확인 권장 |
| `CAUTION` 🔴 | 점수 높음 + 확신도 충분 | 주의 |
| `UNDETERMINED` ⚪ | 아래 "판단 보류가 되는 경우" 전부 | 판단하지 않음 |

**상태 이름은 코드가 쓰는 값이다.** 화면에 보이는 말은 [../packages/content](../packages/content/)에서 고른다.

### 판단 보류(⚪)가 되는 경우

⚪는 **실패가 아니라 결과다.** 사용자에게 오류처럼 보이면 안 된다.

| 원인 | 비고 |
| --- | --- |
| 확신도가 임계값 아래 | 가장 흔한 경우. 모델이 모르겠다고 말한 것 |
| 응답이 정한 보기 밖의 값 | |
| Jev 호출 실패 (429, 5xx) | 재시도 후에도 실패했을 때 |
| 타임아웃 | |
| 네트워크 끊김 | |
| 본문 추출 실패 | 아래 3-2 |
| 본문이 너무 짧음 | 일부 항목만 ⚪. [judgment-items.json](../packages/shared/judgment-items.json)의 `min_body_chars` |

**⚪ 안에서 이유를 구분해 보여 주지 않는다.** 사용자에게 "429를 받았습니다"는 아무 의미가 없다.
다만 **로그에는 남긴다.** 우리가 고쳐야 할 것과 모델이 모르는 것은 다르다.

> **[정함]** ⚪ 상태에서도 **상세를 열 수 있다.** 어느 항목이 판단됐고 어느 항목이 보류인지 보여 준다.
> 전부 보류면 그렇게 적는다.

## 3. ① 기사 자동 검사

기사 페이지를 열면 배지가 뜬다. **제품의 중심 기능이다.**

### 3-1. 흐름

```text
기사 페이지 열림
   │
   ├─ 대상 페이지인가?            아니오 → 아무것도 하지 않는다
   │   (match-patterns.ts)
   ▼
본문 추출                        실패 → ⚪ (3-2)
   │
   ▼
배지를 PENDING 으로 띄운다       ← 여기서 이미 화면에 보인다
   │
   ▼
중계 서버에 판단 요청
   │  (요청 그룹별로 나뉨)
   ▼
응답 → 점수 합산 → 단계 결정      실패·타임아웃 → ⚪
   │  (packages/shared)
   ▼
배지를 결과 상태로 바꾼다
```

**핵심은 "배지를 먼저 띄우고 나중에 바꾼다"는 점이다.** 판단이 끝난 뒤에 띄우면 화면이 늦게 밀린다.

### 3-2. 본문 추출

- 추출 대상은 **제목과 본문**이다. 광고·추천 기사·댓글·내비게이션은 **보내기 전에 걷어낸다** ([jev.md](jev.md) 3절 ⑤)
- **추출에 실패하면 ⚪다.** 추측해서 페이지 전체를 보내지 않는다. 관계없는 내용이 섞이면 판단이 나빠진다
- **[골라야 함]** 추출 방법
  - **A. 사이트별 선택자** — 네이버·다음 각각의 DOM 구조에 맞춘 선택자를 둔다. 정확하지만 사이트가 바뀌면 깨진다
  - **B. 범용 추출 규칙** — 가장 긴 텍스트 블록 등 휴리스틱. 덜 정확하지만 덜 깨진다
  - 대상이 지금 두 사이트뿐이라 **A를 권한다.** 깨지면 ⚪가 뜨고, 그건 우리가 의도한 동작이다

> **TODO**: 네이버·다음 기사 페이지의 제목·본문 선택자를 조사해 적는다. 사이트가 바꾸면 여기를 고친다.

### 3-3. 배지 위치

- **[골라야 함]** 어디에 둘 것인가
  - **A. 화면 우하단 고정** — 기사 내용을 가리지 않는다. 스크롤해도 따라온다. **지금 구현된 방식**
  - **B. 기사 제목 옆에 삽입** — 판단 대상 바로 옆이라 뜻이 분명하다. 대신 사이트 레이아웃을 건드리고, 제목 위치가 사이트마다 달라 깨지기 쉽다
  - **A를 권한다.** 우리 규칙이 *"페이지의 DOM을 고치지 않는다. 우리 요소를 더할 뿐"* 이라 B는 그 규칙과 부딪힌다
- 기사 본문을 가리지 않는다
- **[정함]** Shadow DOM 안에 둔다 (`mode: 'closed'`). 페이지 CSS와 서로 간섭하지 않게 한다

### 3-4. 상세

배지를 누르면 열린다.

- **보여 주는 것**: 걸린 판단 항목과 그 설명. 항목 이름이 아니라 [../packages/content](../packages/content/)의 문구로
- **보여 주지 않는 것**: **점수 숫자.** 정밀해 보이는 숫자는 단정으로 읽힌다 ([product.md](product.md) 6절)
- **[골라야 함]** 근거 문장을 함께 보여 줄 것인가
  - 보여 준다면 Jev에게 **기사 안의 문장을 고르게** 해서(Choice) 그 문장을 인용한다. 생성하지 않는다
  - 장점: "출처가 없습니다"보다 「전문가에 따르면…」을 보여 주는 쪽이 훨씬 설득력 있다
  - 비용: 판단 항목이 하나 늘고 호출이 늘어난다
  - **v1.0.0에 넣을지 v1.1.0으로 미룰지 정해야 한다**
- 인용문을 넣는다면 **반드시 `textContent`로 넣는다.** 남이 쓴 문장이다
- 다시 누르면 닫힌다

### 3-5. 닫기와 다시 보기

- **[정함]** 사용자가 배지를 닫을 수 있다. 기사를 읽는 데 방해가 되면 안 된다
- **[골라야 함]** 닫았을 때의 범위
  - A. 그 페이지에서만 (새로고침하면 다시 뜸)
  - B. 그 기사에서 계속 (기억함)
  - C. 설정에서 끌 때까지 전체
  - **A를 권한다.** 가장 단순하고, 기억하려면 저장이 필요하다

### 3-6. 같은 기사를 다시 열면

- **[정함]** 캐시한다. 같은 기사를 다시 열 때마다 호출하면 레이트 리밋과 비용이 늘고 응답도 느리다
- 캐시 키는 **기사 URL**
- 캐시에 **기사 본문을 넣지 않는다.** URL과 판단 결과까지다 ([security/secure-coding.md](security/secure-coding.md) 6절)
- **[골라야 함]** 유효 기간 — 기사는 수정된다. **6시간**을 제안한다
- 캐시된 결과를 쓸 때도 **PENDING을 거치지 않고 바로 결과를 보여 준다**

## 4. ② 포털 목록 일괄 검사

네이버·다음 뉴스 목록에서 **제목만** 판단해 낚시성 제목을 표시한다.

### 4-1. 🔴 레이트 리밋 — 먼저 풀어야 할 문제

| | 초당 요청 | 기사 25개에 걸리는 시간 |
| --- | --- | --- |
| ChatKHU Gateway (지금 쓰는 경로) | **2** | **12초 이상** |
| TypeSafe 직접 | 80 | 1초 미만 |

**이 기능만 레이트 리밋에 걸린다.** ①은 기사 하나에 요청 3건 정도라 여유가 있다.

- **[골라야 함]** 셋 중 하나
  - **A. TypeSafe 직접 계약** — 계정 발급·약관 확인이 필요하다. 근본 해결
  - **B. 점진 표시** — 화면에 보이는 것부터 순서대로 칠한다. 12초가 걸려도 사용자는 위에서부터 채워지는 것을 본다. 스크롤해서 내려가면 그때 그 항목을 판단한다
  - **C. v1.1.0으로 미룸**
  - **B가 현실적이다.** 목록을 한 번에 다 칠할 이유가 없다. 사용자는 화면에 보이는 몇 개만 본다

### 4-2. 동작

- 목록에서는 **본문을 읽지 않는다.** 제목으로 판단할 수 있는 항목만 쓴다 (`request_group`에 `portal_list`가 있는 항목)
- **표시를 기사 배지보다 약하게 한다.** 근거가 제목뿐이다
- **[정함]** 포털은 목록을 동적으로 다시 그린다. `MutationObserver`로 따라가되 **우리가 넣은 요소에 다시 반응해 무한 루프가 돌지 않게** 한다
- **[정함]** 같은 제목을 두 번 판단하지 않는다 (①과 같은 캐시를 쓴다)

## 5. ③ 선택 텍스트 검사

드래그한 글을 오른쪽 클릭 메뉴로 검사한다. **기사 페이지가 아닌 곳**(메신저, SNS, 커뮤니티)에서도 쓸 수 있다.

- 메뉴는 **글을 선택했을 때만** 뜬다
- 고른 글은 `body` 필드에 넣는다. `source_citation`은 보내지 않는다 — 출처가 고른 글 밖에 있기 쉽다 ([packages/shared/README.md](../packages/shared/README.md))
- **입력이 짧아 ⚪가 자주 나오는 것이 정상이다.** 그렇게 보여 준다
- **[골라야 함]** 결과를 어디에 보여 줄 것인가
  - A. 선택한 글 근처에 떠 있는 작은 상자
  - B. 확장 팝업 (툴바 아이콘)
  - C. 크롬 알림
  - **A를 권한다.** 사용자가 보던 자리에서 바로 보인다. 다만 임의의 사이트에 주입하는 것이라 Shadow DOM이 더 중요해진다
- **[정함]** 아주 긴 글을 선택하면 거절한다. 상한을 넘기면 "너무 깁니다"를 보여 준다

## 6. ④ 공유 직전 알림

🔴로 판단된 기사를 복사하거나 공유하려 할 때 알린다.

- **[정함] 공유를 막지 않는다.** 버튼을 가리거나 동작을 취소하지 않는다. 알림은 닫으면 그만이다
- **[정함]** 🔴에만 띄운다. ⚪·🟢·🟡에는 띄우지 않는다
- **[정함]** 같은 기사에 반복해서 띄우지 않는다
- **[골라야 함]** 무엇을 "공유"로 볼 것인가
  - A. URL 복사 (`copy` 이벤트에 기사 주소가 포함)
  - B. 페이지의 공유 버튼 클릭
  - C. 둘 다
  - **A를 권한다.** B는 사이트마다 버튼이 달라 전부 따라가기 어렵다
- **[골라야 함]** 알림을 어떻게 띄울 것인가
  - A. 페이지 안 작은 알림 (Shadow DOM) — 권한이 필요 없다
  - B. `chrome.notifications` — 권한이 하나 늘어난다
  - **A를 권한다.** 권한 최소화 규칙과 맞고, 사용자가 보던 자리에 뜬다

## 8. 전역 규칙

### 성능

- **배지는 먼저 뜨고 나중에 바뀐다.** 판단을 기다렸다가 띄우지 않는다
- **[골라야 함]** 판단 요청을 언제 보낼 것인가
  - A. 페이지가 열리자마자
  - B. 사용자가 조금 읽은 뒤 (스크롤·체류 시간)
  - **A를 권한다.** B는 호출을 아끼지만 배지가 늦게 뜬다. "읽는 순간에 알려 준다"는 제품의 전제와 맞지 않는다

> **TODO**: 배지가 결과로 바뀌기까지의 목표 시간. 실측 후 정한다 ([jev.md](jev.md) 6-1절에 질문 2개 0.86초 기록).

### 하지 않는 것

[product.md](product.md) 2절의 전제가 모든 기능에 적용된다.

- 진위를 단정하지 않는다 — "가짜", "허위", "거짓"을 쓰지 않는다
- 공유를 막지 않는다
- 모르면 모른다고 한다 (⚪)
- 동의 없이 아무것도 보내지 않는다
- **기사 페이지의 DOM을 고치지 않는다.** 우리 요소를 더할 뿐이다

### 설정

**[골라야 함]** v1.0.0에 설정 화면을 넣을 것인가.

- 넣는다면: 기능별 켜기/끄기, 피드백 동의 여부
- 안 넣는다면: 전부 켜진 상태로 고정. 피드백 동의는 보낼 때마다 묻는다
- **안 넣는 쪽을 권한다.** 설정이 없으면 만들 것도 테스트할 것도 준다
