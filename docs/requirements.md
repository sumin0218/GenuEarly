## 2. 배지 상태

**배지는 항상 이 중 하나다.** 상태가 없는 순간은 없다 — 페이지에 붙는 순간부터 무언가를 보여 준다.

| 상태 | 언제 | 사용자에게 |
| --- | --- | --- |
| `PENDING` | 판단 요청을 보냈고 기다리는 중 | 판단 중임을 알리는 표시 |
| `SAFE` 🟢 | 점수 낮음 + 확신도 충분 | 안심 |
| `CHECK` 🟡 | 점수 중간, 또는 확신도 애매 | 확인 권장 |
| `CAUTION` 🔴 | 점수 높음 + 확신도 충분 | 주의 |
| `UNDETERMINED` ⚪ | 아래 "판단 보류가 되는 경우" 전부 | 판단하지 않음 |

**상태 이름은 코드가 쓰는 값이다.** 화면에 보이는 말은 [../packages/content](../packages/content/)에서 고른다.

### 판단 보류(⚪)가 되는 경우

⚪는 **실패가 아니라 결과다.** 사용자에게 오류처럼 보이면 안 된다.

| 원인 | 비고 |
| --- | --- |
| 확신도가 임계값 아래 | 가장 흔한 경우. 모델이 모르겠다고 말한 것 |
| 응답이 정한 보기 밖의 값 | |
| Jev 호출 실패 (429, 5xx) | 재시도 후에도 실패했을 때 |
| 타임아웃 | |
| 네트워크 끊김 | |
| 본문 추출 실패 | 아래 3-2 |
| 본문이 너무 짧음 | 일부 항목만 ⚪. [judgment-items.json](../packages/shared/judgment-items.json)의 `min_body_chars` |

**[정함] ⚪ 안에서 이유를 구분해 보여 주지 않는다.** 사용자에게 "429를 받았습니다"는 아무 의미가 없다.
다만 **로그에는 남긴다.** 우리가 고쳐야 할 것(네트워크·타임아웃)과 모델이 모르는 것(확신도 낮음)은 완전히 다른 문제다.

**[정함]** ⚪ 상태에서도 **상세를 열 수 있다.** 어느 항목이 판단됐고 어느 항목이 보류인지 보여 준다.
전부 보류면 그렇게 적는다.

## 3. ① 기사 자동 검사

기사 페이지를 열면 배지가 뜬다. **제품의 중심 기능이다.**

### 3-1. 흐름

```text
기사 페이지 열림
   │
   ├─ 대상 페이지인가?            아니오 → 아무것도 하지 않는다
   │   (match-patterns.ts)
   ▼
캐시 확인                        있음 → 바로 결과 표시 (PENDING 생략)
   │
   ▼
본문 추출                        실패 → ⚪ (3-2)
   │
   ▼
배지를 PENDING 으로 띄운다       ← 여기서 이미 화면에 보인다
   │
   ▼
중계 서버에 판단 요청
   │  (요청 그룹별로 나뉨)
   ▼
응답 → 점수 합산 → 단계 결정      실패·타임아웃 → ⚪
   │  (packages/shared)
   ▼
배지를 결과 상태로 바꾼다 → 캐시에 저장
```

**핵심은 "배지를 먼저 띄우고 나중에 바꾼다"는 점이다.** 판단이 끝난 뒤에 띄우면 화면이 늦게 밀린다.

### 3-2. 본문 추출

**[정함] 사이트별 선택자를 쓴다.**

대상이 네이버·다음 둘뿐이라 범용 휴리스틱보다 정확하다. 사이트가 구조를 바꾸면 깨지는데,
**깨지면 ⚪가 뜨고 그건 우리가 의도한 동작이다.** 틀린 판단을 내놓는 것보다 낫다.

- 추출 대상은 **제목과 본문**이다. 광고·추천 기사·댓글·내비게이션은 **보내기 전에 걷어낸다** ([jev.md](jev.md) 3절 ⑤)
- **추출에 실패하면 ⚪다.** 추측해서 페이지 전체를 보내지 않는다. 관계없는 내용이 섞이면 판단이 나빠진다
- 선택자는 한곳에 모은다. 사이트가 바뀌면 거기만 고친다

> **TODO**: 네이버·다음 기사 페이지의 제목·본문 선택자를 조사해 적는다.

### 3-3. 배지 위치

**[정함] 화면 우하단 고정.**

- 기사 본문을 가리지 않고, 스크롤해도 따라온다
- **제목 옆 삽입을 기각한 이유는 "제목 위치가 사이트마다 달라 깨지기 쉽다"는 것이다.** 우리 규칙("우리 요소를 더할 뿐")과 부딪혀서가 아니다 — 그 규칙은 요소를 더하는 것을 허용하고, 실제로 ②(4-2)는 목록의 제목마다 표시를 넣는다
- **Shadow DOM 안에 둔다** (`mode: 'closed'`). 페이지 CSS와 서로 간섭하지 않게 한다

### 3-4. 상세

배지를 누르면 열린다. 다시 누르면 닫힌다.

- **보여 주는 것**: 걸린 판단 항목과 그 설명. 항목 이름이 아니라 [../packages/content](../packages/content/)의 문구로
- **보여 주지 않는 것**: **점수 숫자.** 정밀해 보이는 숫자는 단정으로 읽힌다 ([product.md](product.md) 6절)

**[정함] 근거 문장 인용은 v1.1.0으로 미룬다.**

기사 속 문장을 Jev에게 고르게 해서(Choice) 보여 주면 설득력이 크게 오른다. 생성이 아니라 선택이라
지어낼 수도 없다. 다만 **판단 항목이 하나 늘고 호출이 늘며 [judgment-items.json](../packages/shared/judgment-items.json)을
다시 열어야 한다.** 그 스키마는 이미 확정됐고, 지금 다시 여는 비용이 크다.
v1.0.0은 항목별 설명문만 보여 준다.

### 3-5. 닫기와 다시 보기

- **[정함]** 사용자가 배지를 닫을 수 있다. 기사를 읽는 데 방해가 되면 안 된다
- **[정함] 닫기는 그 페이지에서만 유효하다.** 새로고침하면 다시 뜬다
  - 기억하려면 저장이 필요하고, "어느 범위로 기억하는가"를 또 정해야 한다. 가장 단순한 쪽을 고른다

### 3-6. 같은 기사를 다시 열면

- **[정함] 캐시한다.** 같은 기사를 다시 열 때마다 호출하면 레이트 리밋과 비용이 늘고 응답도 느리다
- **[정함] 캐시는 판단 항목 단위로 쌓는다.** 기사 단위가 아니다

  ②는 제목만 보는 항목(`clickbait_headline`, `spread_inducement`)만 판단한다. 이걸 기사 단위로
  캐시하면, 사용자가 목록에서 그 기사를 눌렀을 때 **"캐시 있음"으로 보고 출처·제목-본문 일치·문장
  판단을 건너뛴 채 제목만 본 결과가 6시간 동안 기사 배지로 나온다.**

  그래서 이렇게 한다.
  - 캐시 값에 **항목별 결과**를 담는다
  - ①은 **없는 항목만** 요청한다. ②가 채워 둔 항목은 재사용한다
  - **①에 필요한 항목이 모두 채워졌을 때만** "캐시 있음"으로 본다
- 캐시에 **기사 본문을 넣지 않는다.** 판단 결과까지다 ([security/secure-coding.md](security/secure-coding.md) 6절)
- **[정함] 유효 기간 6시간.** 기사는 수정된다. 하루를 넘기면 수정된 기사를 옛 판단으로 보여 줄 위험이 커지고,
  1시간은 짧아 캐시가 거의 안 먹는다. **근거가 약한 값이라 실제 사용을 보고 조정한다**
- 캐시된 결과를 쓸 때는 **PENDING을 거치지 않고 바로 결과를 보여 준다**
- 키 형태와 URL 정규화는 [architecture.md](architecture.md) 6절에 있다

## 4. ② 포털 목록 일괄 검사

**[정함] 목록 전체를 한 번에 치지 않는다.**

### 4-2. 동작

- 목록에서는 **본문을 읽지 않는다.** 제목으로 판단할 수 있는 항목만 쓴다 (`request_group`에 `portal_list`가 있는 항목)

## 5. ③ 선택 텍스트 검사

드래그한 글을 오른쪽 클릭 메뉴로 검사한다. **기사 페이지가 아닌 곳**(메신저, SNS, 커뮤니티)에서도 쓸 수 있다.

- 메뉴는 **글을 선택했을 때만** 뜬다
- 고른 글은 `body` 필드에 넣는다. `source_citation`은 보내지 않는다 — 출처가 고른 글 밖에 있기 쉽다 ([packages/shared/README.md](../packages/shared/README.md))
- **입력이 짧아 ⚪가 자주 나오는 것이 정상이다.** 그렇게 보여 준다
- **[정함]** 아주 긴 글을 선택하면 거절한다. 상한을 넘기면 "너무 깁니다"를 보여 준다

### 5-1. 결과 위치

**[정함] 선택한 글 근처에 띄운다.**

사용자가 보던 자리에서 바로 보이는 쪽을 골랐다. 확장 팝업은 클릭이 한 번 더 필요하다.

**대신 ①보다 까다롭다.** ①은 네이버·다음 두 사이트만 상대하지만, 이건 **임의의 사이트에 UI를 주입**한다.

- **Shadow DOM이 ①보다 더 중요하다.** 어떤 사이트의 CSS가 우리 UI를 어떻게 망가뜨릴지 모른다. `mode: 'closed'`를 반드시 지킨다
- `position`과 `z-index`를 사이트와 충돌하지 않게 잡아야 한다. 선택 영역 좌표는 `Range.getBoundingClientRect()`로 구한다
- 스크롤하거나 선택이 풀리면 닫는다
- **권한**: 두 개가 필요하다.
  - **`activeTab`** — 사용자가 메뉴를 누른 그 탭에만, 그 순간에만 접근한다. `<all_urls>`를 피하기 위해서다
  - **`scripting`** — `activeTab` 은 접근 권한만 준다. 그 탭에 우리 UI 를 넣으려면 `chrome.scripting.executeScript` 를 불러야 하고, 그 API 가 이 권한을 따로 요구한다. 정적 `content_scripts` 로 임의의 사이트에 붙이려면 `<all_urls>` 가 필요하므로 그 길은 쓰지 않는다
  - 선택한 글 자체는 `contextMenus.onClicked` 의 `info.selectionText` 로 받는다. 주입이 필요한 것은 **UI 뿐이다**

## 6. ④ 공유 직전 알림

🔴로 판단된 기사를 복사하거나 공유하려 할 때 알린다.

- **[정함] 공유를 막지 않는다.** 버튼을 가리거나 동작을 취소하지 않는다. 알림은 닫으면 그만이다
- **[정함]** 🔴에만 띄운다. ⚪·🟢·🟡에는 띄우지 않는다
- **[정함]** 같은 기사에 반복해서 띄우지 않는다

### 6-1. 무엇을 "공유"로 보는가

**[정함] 사이트의 공유·URL 복사 버튼 클릭을 듣는다.** 네이버·다음 두 곳의 선택자를 둔다.

처음에는 `copy` 이벤트만 보기로 했는데 **그 방법으로는 사람들이 실제로 쓰는 경로를 거의 못 잡는다.**

| 공유 방법 | `copy` 이벤트가 뜨나 |
| --- | --- |
| 주소창에서 복사 | ❌ 주소창은 페이지 밖이라 content script 에 이벤트가 오지 않는다 |
| 사이트의 "URL 복사" 버튼 | ❌ `navigator.clipboard.writeText()` 는 `copy` 이벤트를 발생시키지 않는다 |
| 본문에서 URL 글자를 드래그해 복사 | ✅ 하지만 기사 본문에 그 기사 주소가 적힌 경우는 드물다 |

그대로 두면 **시연에서 거의 보이지 않는 기능**이 된다.

대상이 네이버·다음 두 사이트뿐이고 **이미 본문 추출에 사이트별 선택자를 쓰기로 했다**(3-2).
공유 버튼 선택자 몇 개를 더 두는 비용이 크지 않다.

- `copy` 이벤트도 **함께** 듣는다. 본문에서 주소를 긁어 복사하는 경우를 덤으로 잡는다
- 주소창 복사는 **잡지 못한다.** 브라우저가 확장에 그 사건을 주지 않는다. 알려진 한계로 둔다

### 6-2. 어떻게 띄우는가

**[정함] 페이지 안 알림(Shadow DOM).** `chrome.notifications` 권한을 받지 않는다.

## 7. ⑤ 오판 피드백

판단이 틀렸다고 알려 줄 수 있다.

- **[정함] 사용자가 동의한 경우에만 보낸다.** 기본값은 보내지 않는 것이다
- **[정함]** 무엇을 보내는지 **보내기 전에 그대로 보여 주고** 동의를 받는다
- **[정함]** 기사 본문 전체를 보내지 않는다
- **[정함]** 사용자를 식별할 수 있는 값을 만들지 않는다. 설치 ID·계정·광고 ID 전부

## 8. 전역 규칙

### 8-1. 레이트 리밋 — 미해결

**이것은 ② 만의 문제가 아니다.** 처음에는 그렇게 적었는데 틀렸다.

#### 기사 하나(①)에 몇 건이 나가나

[judgment-items.json](../packages/shared/judgment-items.json)에서 센 값이다.

| 요청 그룹 | 건수 |
| --- | --- |
| `headline_only` | 1 |
| `headline_body` | 1 |
| `sentence` (`unverifiable_claim`) | **문장마다 1건** |

```
문장 10개 기사 → 12건 → 초당 2건이면  6초
문장 20개 기사 → 22건 →              11초
문장 30개 기사 → 32건 →              16초
```

**그리고 초당 2건은 기능별 한도가 아니라 키 하나에 걸린 한도다.**
중계 서버는 ChatKHU 키 하나로 모든 사용자의 요청을 보낸다. 심사위원 여러 명이나
전시장 방문객이 동시에 기사를 열면 그 2건을 **모두가 나눠 쓴다.**

#### 줄일 수 있는 것

| 방법 | 효과 | 한계 |
| --- | --- | --- |
| **문장 수 상한** (앞쪽 N문장만) | 요청 수가 예측 가능해진다 | N=10 이어도 12건 6초 |
| **2단계 표시** — 고정 2건으로 먼저 배지를 내고, 문장 결과로 갱신 | 첫 배지가 1초 안에 뜬다 | 배지가 사용자 눈앞에서 바뀐다 |
| ② 점진 표시 (4-1) | 목록이 위에서부터 채워진다 | ①에는 도움이 안 된다 |

**셋을 다 해도 동시 사용자 문제는 남는다.** 전시장에서 열 명이 동시에 기사를 열면
한 사람당 초당 0.2건이다.

**[TypeSafe 직접 계약(초당 80건)을 "안 하기로 한 결정"에서 "미정"으로 되돌린다.**
