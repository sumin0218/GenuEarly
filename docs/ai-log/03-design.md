# 03. 기획·설계

> 서식4의 **기획·설계** 단계다. 형식과 규칙은 [README.md](README.md)에 있다.
> 항목 하나가 결정 하나다. 최신 항목을 아래에 덧붙인다.

무엇을 어떻게 판단할지 정한 과정. **ChatKHU의 주 역할이 여기다.**

두 가지가 여기 들어간다.

1. **판단 기준** — 어떤 신호를 볼 것인가. 결론은 [../product.md](../product.md) 4절의 판단 항목 표
2. **Jev 질문 설계** — 그 기준을 `instructions`·`criteria`·보기로 옮긴 것. 결론은 [../../packages/shared/](../../packages/shared/)

## 이 단계에서 사람이 쥐고 있어야 할 것

### 판단 기준

- **항목이 서로 독립인가.** 같은 것을 두 번 세면 점수가 부풀려진다
- **그 항목이 가짜의 신호가 맞는가.** 예: `ai_style_signal`이 높다고 가짜가 아니다. 기계로 쓴 진짜 기사가 많다
- **코드가 더 정확히 할 수 있는 일을 모델에 넘기지 않았는가.** 출처 도메인 대조가 그 예다
- 항목마다 **틀렸을 때 사용자가 치르는 대가**가 다르다. 가중치는 그걸 반영해야 한다

### Jev 질문 설계

[../jev.md](../jev.md) 3절의 한계가 전부 여기서 걸린다.

- **문자 그대로 읽는다** — 조건을 끝까지 적었는가. 틀린 답에 "내 말은 그게 아니라"라고 설명하고 싶어졌다면 그 설명이 빠진 지시문이다
- **보기 순서 편향** — 순서를 바꿔 보고 답이 그대로인지 확인했는가
- **instructions와 criteria가 어긋나지 않았는가**
- **한 질문에 한 판단만 담았는가**
- **적대적 입력** — 기사 본문을 `instructions`에 이어 붙이지 않았는가

프롬프트를 고칠 때마다 **무엇을 왜 고쳤는지**를 남긴다. 프롬프트는 되돌리기 쉬운 만큼 왜 그렇게 됐는지를 가장 빨리 잊는다.

### 판단 항목 7개를 Jev 질문으로 작성 (GE-12)

- **날짜**: 2026-10-17
- **AI 모델**: 코딩 도구 (Claude Code / Claude Opus 5.5)
- **외부 도구 사용 사유**: 판단 기준 설계는 ChatKHU의 주 역할이다. 이번에는 [../jev.md](../jev.md) 3절의 설계 규칙 9개와 [../product.md](../product.md) 4절 초안을 저장소에서 함께 읽고, 결과를 [../../packages/shared/judgment-items.json](../../packages/shared/judgment-items.json)과 문서에 바로 반영하는 작업이라 저장소를 직접 읽고 쓰는 코딩 도구로 초안을 만들었다. **문구 검토는 ChatKHU로 따로 한다** (아래 TODO).
- **주요 프롬프트**: "product.md 4절의 판단 항목 7개를 Jev 질문으로 확정하라. 항목마다 `instructions`와 `criteria`를 쓰고, Choice 보기와 순서를 상수로 고정하라. 한 질문에 한 판단, 부정문 금지, 기사 글은 `state` 필드에만, jev.md 3절 규칙을 따를 것"

- **사람이 결정·수정한 것**: 작업 전에 코딩 도구가 "결정할 것" 6가지와 추천안을 정리했고, 사용자가 검토해 6가지 모두 추천안대로 채택했다. 그중 판단과 관련된 것은 아래와 같다.
  - **보기 상수를 TS 코드가 아니라 JSON으로 둔다.** `packages/shared`는 확장 프로그램과 중계 서버 양쪽에서 돌아야 하는데, 중계 서버 스택이 아직 미정이다. 코드로 쓰면 스택을 추측하게 된다.
  - **질문만 확정하고 가중치·배지 경계·확신도 임계값은 범위 밖으로 남긴다.** 셋 다 eval 측정값이 있어야 정할 수 있다.
  - **지시문은 한국어로 쓴다.** 입력이 전부 한국어 기사이고, GE-29에서 게이트웨이로 부른 한국어 질문이 동작했다. 영어 지시문과의 비교는 [../jev.md](../jev.md) 4절의 TODO로 그대로 둔다.
  - **초안은 코딩 도구로 쓰고, ChatKHU 검토와 Jev 호출 확인은 뒤로 미룬다** (아래 TODO).
  - 기록 위치는 Jira 이슈에 적힌 `02-criteria.md`·`03-prompt.md`가 아니라 이 파일이다. 서식4에 맞춰 두 파일이 `03-design.md`로 합쳐졌기 때문이다.
- **코딩 도구가 초안에서 정한 설계와 그 이유** — 사람이 아직 검토하지 않았다. 문구를 검토할 때 볼 곳이다.
  - **Choice 보기는 주의 신호 쪽을 앞에 두었다.** jev.md 3절 ⑧의 "유리한 보기를 맨 앞에 두지 않는다"를 따랐다. 반대로 주의 쪽으로 기울 수 있으므로, eval의 "보기 순서 바꾸기" 검사로 확인해야 한다.
  - **부정문을 질문과 보기에서 뺐다.** "출처가 없는가" 대신 "어떤 방식으로 밝히는가"로 묻고, 없음은 "출처 표현 부재"처럼 명사로 적었다. `unverifiable_claim`도 "확인할 수 없는 주장인가" 대신 "근거를 생략하거나 이름이 빠진 출처에만 기대는가"로 바꿨다. Noul의 "예"가 주의 신호와 같은 방향이 되게 했다 (jev.md 3절 ⑦).
  - **Score는 등급 4개로 했다.** 홀수면 가운데 등급으로 몰릴 수 있다고 봤다. 근거는 측정이 아니라 추정이다. eval에서 확인한다.
  - **항목끼리 겹치는 부분을 `criteria`로 갈랐다.** `headline_body_match`는 내용만 비교하고 말투는 보지 않는다. `clickbait_headline`은 제목 글자만 보고 본문과의 일치는 보지 않는다.
  - **`unverifiable_claim`은 `sentence` 필드 하나만 본다.** 출처가 앞 문장에 있는 경우("그는 이렇게 말했다")에 예가 늘 수 있다. 문맥을 함께 넣으려면 기사 글을 질문 안에 넣거나 `state`를 키워야 하는데, 둘 다 jev.md 3절 ⑤·⑥에 걸린다. 그래서 알려진 한계로 두고 eval에서 크기를 잰다.
  - `source_citation`(본문 단위)과 `unverifiable_claim`(문장 단위)은 둘 다 출처를 본다. 같은 신호를 두 번 셀 수 있으므로 가중치를 정할 때 함께 본다.

### 판단 항목 질문을 코드 리뷰 지적에 맞춰 고침 (GE-12)

- **날짜**: 2026-10-17
- **AI 모델**: 코딩 도구 (Claude Code / Claude Opus 5.5) — 리뷰와 수정 모두
- **외부 도구 사용 사유**: 위 항목과 같다. jev.md 규칙과 질문 문구를 대조하는 리뷰라서 저장소를 직접 읽는 도구로 했다.
- **주요 프롬프트**: PR #7을 리뷰하게 하고("jev.md 3·5절 규칙과 문구를 대조하라"), 달린 지적 10건을 반영하게 했다.
- **결과**: 리뷰 지적은 P2 2건, P3 6건, P4 2건이었다. 코딩 도구가 10건을 모두 아래처럼 고쳤다. 첫 초안이 놓친 곳은 리뷰가 찾아냈다.
  - **주의 보기를 맨 앞에 둔 첫 초안을 뒤집었다.** 첫 초안은 jev.md ⑧의 "유리한 보기를 맨 앞에 두지 않는다"만 보고, 5절의 "🔴이 🟢보다 대가가 크다"를 놓쳤다. 맨 앞으로 기우는 편향을 대가가 큰 쪽으로 고정한 셈이다. **가운데 보기를 맨 앞에** 두어 기울어도 🟡로 가게 했다. 두 순서로 보내 평균하는 방법은 eval로 비교할 TODO로 남겼다.
  - **보기마다 `signal`(caution/neutral/clear)을 넣었다.** 순서만으로 방향을 나타내면, eval에서 순서를 바꾸는 순간 방향도 사라진다. 항목마다 뜻이 반대였던 `absent`는 `no_source`·`no_spread`로 나눴다.
  - **`unverifiable_claim`을 Noul 두 개로 나눴다** — `factual_assertion`(사실 단정인가)과 `named_basis`(이름 있는 근거가 문장 안에 있는가). 첫 초안은 "단정 + 근거 생략 또는 익명 출처"를 한 질문에 묶어, jev.md의 "한 질문에 여러 판단 숨기기"에 걸렸다. 판단 항목 이름은 7개 그대로 두고 코드가 `P(단정) × (1 − P(근거))`로 합친다.
  - **"일반 상식이면 아니오" 기준을 뺐다.** 공통 `criteria`("사실 여부는 판단 범위 밖")와 정면으로 충돌했다. 상식 문장이 얼마나 걸리는지는 eval에서 잰다.
  - **본문이 짧은 기사는 `headline_body_match`를 ⚪로 둔다.** 첫 초안은 "제목 내용이 본문에 빠져 있음"을 가장 강한 주의 보기로 보냈다. 그러면 포토 기사나 단신처럼 정보가 부족할 뿐인 기사가 🔴 쪽으로 갔다. 빠진 경우는 가운데 보기로 옮기고, 기준 길이(`min_body_chars`)는 eval 후에 정한다.
  - **다른 언론사·통신사 인용을 특정된 출처로 명시했다.** "기자와 언론사의 이름은 제외"가 "연합뉴스에 따르면"까지 지울 수 있었다. Jev가 문자 그대로 읽는다는 한계(jev.md ①)를 첫 초안이 놓친 곳이다.
  - **제목만 보는 질문은 따로 보낸다.** jev.md ⑤(필요한 필드만)와 6절(한 요청에 묶기)이 부딪히는데 ⑤를 우선했다. `request_group`으로 적어 두었다.
  - **③ 선택 텍스트에서 `source_citation`을 뺐다.** 고른 한두 문장 밖에 출처가 있기 쉬워 구조적으로 "출처 부재"가 나온다.
  - product.md 표에서 보기 문구를 지우고 JSON 링크로 대신했다(원본 하나 원칙). 중계 서버가 `JEV_MODEL`과 이 파일의 `model`이 다르면 경고를 남기도록 README에 적었다.
- **사람이 결정·수정한 것**:
  - 머지 전에 PR 리뷰를 받기로 하고, 리뷰를 사용자 계정 댓글로 PR에 남기게 했다.
  - 지적 10건을 읽고 모두 받아들이기로 했다. 반영 방식은 코딩 도구가 정했다.
  - 반영 뒤 스레드마다 답글을 달고 resolve하게 한 뒤, 같은 기준으로 다시 리뷰를 받았다 (아래 항목).

### 판단 항목 질문 2차 리뷰 반영 (GE-12)

- **날짜**: 2026-10-17
- **AI 모델**: 코딩 도구 (Claude Code / Claude Opus 5.5) — 리뷰와 수정 모두
- **외부 도구 사용 사유**: 위 항목과 같다.
- **주요 프롬프트**: 1차 반영 커밋을 기준으로 PR #7을 다시 리뷰하게 하고, 달린 지적 6건을 반영하게 했다.
- **결과**: 지적은 P2 1건, P3 3건, P4 2건이었다. 코딩 도구가 6건을 모두 아래처럼 고쳤다. 1차 반영이 새로 만든 문제가 대부분이다.
  - **`unverifiable_claim`의 ⚪ 규칙을 정했다.** 1차에서 두 Noul 확률을 곱하게 했는데, 곱한 값은 "0.5에서의 거리"라는 확신도의 뜻을 잃는다. 둘 다 0.5(모름)면 0.25가 되어 확신한 것처럼 읽힌다. 질문 중 하나라도 보류 구간이면 그 문장은 ⚪로 두고, 둘 다 확신 구간일 때만 곱을 쓴다(`undetermined_rule`).
  - **`request_group`을 기능별 값으로 바꿨다.** `spread_inducement`는 ①에서는 `article`, ②에서는 `headline_only`로 가는데 값이 하나뿐이라 그 예외를 코드가 따로 적어야 했다. 기능을 키로 쓰니 `features` 필드와 겹쳐서 `features`는 지웠다.
  - **짧은 본문 예외를 `article` 요청 그룹 전체로 옮겼다.** `headline_body_match`에만 걸어 두면 `source_citation`이 짧은 본문에서 여전히 "출처 부재"(주의)를 냈다.
  - `unit` 설명과 이 기록의 서술을 바로잡았다. 이전 두 항목의 "사람이 결정·수정한 것" 칸에 코딩 도구가 정한 내용이 사람의 판단처럼 적혀 있어서, 사람이 실제로 한 일만 남기고 나머지는 결과 칸으로 옮겼다.
  - `version`은 1.0.0으로 유지했다. 머지 전이고 첫 커밋의 질문 세트로 Jev를 호출하거나 기록한 결과가 없다.
- **사람이 결정·수정한 것**:
  - 1차 반영 뒤 다시 리뷰를 받기로 했다. P2가 또 나와서 반영 뒤 한 번 더 리뷰를 받기로 했다.
  - 지적 6건을 모두 받아들이기로 했다. 반영 방식은 코딩 도구가 정했다.

  - **⚪ 판정에 순서를 넣었다.** 2차에서 정한 규칙은 질문 하나라도 "모름"이면 ⚪였는데, 의견 문장(단정 아님)이나 실명 출처 문장(근거 있음)은 질문 하나로 결과가 정해진다. 그런 문장까지 ⚪로 보내면 문장 단위 ⚪ 비율이 쓸데없이 오른다. 결과를 정하는 답이 있으면 먼저 끝내고, 그 밖에 "모름"이 있으면 ⚪, 둘 다 확신일 때만 곱을 쓴다.
  - **`combine`과 보류 구간을 코드가 읽는 값으로 바꿨다** (`op`, `a`, `b`, `undetermined_band`). 판정 순서만 `op`별로 코드에 둔다.
  - **본문이 짧을 때 `spread_inducement`는 제목만으로 묻는다** (`short_body_fallback`). 같은 기사가 ② 목록과 ① 기사 화면에서 다른 판단을 받지 않게 하기 위해서다.
  - **`min_body_chars`를 기능별로 나눴다.** ③은 한두 문장을 고르므로 ①의 포토·단신 기준을 쓰면 ③의 Score 항목이 거의 항상 ⚪가 된다.
  - **이름이 세 뜻으로 겹치던 `article`을 나눴다.** 기능 키는 `page`, 요청 그룹은 `headline_body`로 바꿨다. 항목의 `state_fields`는 `basis_fields`(판단 근거 필드)로 이름을 바꾸고, `state` 구성은 그룹만 정한다고 적었다.
  - 이 기록의 첫 항목이 첫 초안을 "v1.0.0"이라 부르던 것을 "첫 초안(머지 전, 버전 없음)"으로 고쳤다. v1.0.0은 머지되는 최종 세트에만 쓴다.
- **사람이 결정·수정한 것**:
  - 3차 리뷰를 마지막 리뷰로 정하고, 지적 7건을 모두 받아들이기로 했다. 반영 방식은 코딩 도구가 정했다.

### 판단 스키마를 실제 Jev API 형식으로 교정 (GE-31)

- **날짜**: 2026-10-21
- **AI 모델**: 코딩 도구 (Claude Code / Claude Opus 5) — 원인 추적과 수정
- **외부 도구 사용 사유**: 위 항목과 같다.
- **주요 프롬프트**: GE-11(응답 시간·토큰 측정)을 위해 질문 세트로 실제 호출을 하게 했다. 요청 20건이 전부 400으로 돌아왔다.
- **결과**: **질문 세트 v1.0.0이 Jev API에 보낼 수 없는 형식이었다.** 3차까지의 리뷰는 판단 내용만 보고 전송 형식은 아무도 확인하지 않았다. 실제로 한 번 부르기 전까지 드러나지 않았다.
  - `options`와 `grades`는 **API에 없는 필드다.** OpenAPI 명세(`https://docs.typesafe.ai/api.md`)의 `ChoiceQuestion`·`ScoreQuestion`에 그런 이름이 없다. 보기는 전부 `criteria`가 담는다.
  - `criteria`는 유형마다 모양이 다르다. Choice는 **객체** `{보기이름: 설명}`, Score는 **배열**(자리가 곧 점수), Noul은 **키가 `true`·`false`뿐인 객체**다. v1.0.0은 셋 다 자유 서술 배열로 적고 있었다.
  - 고친 방식: `question` 객체를 항목 안에 두고 **그것을 API에 그대로 보낸다.** 우리 형식을 따로 만들고 변환하지 않는다. 변환 계층이 있으면 다음에 또 어긋났을 때 어디가 틀렸는지 찾기 어렵다. 코드가 하는 일은 `instructions` 뒤에 `common_instructions`를 붙이는 것 하나다.
  - **판단 내용은 그대로 두었다.** 보기 이름, 보기 순서, 묻는 말, 등급 수를 바꾸지 않았다. 자유 서술 `criteria`에 있던 문장은 내용에 따라 나눠 옮겼다 — 특정 보기를 가리는 기준은 그 보기의 설명으로, 보기를 가리지 않는 일반 규칙은 `instructions`로.
  - `signal`은 보기 설명 안에 있을 자리가 없어 `signals` 맵으로 `question` 밖에 뺐다. **API에 보내는 것과 우리가 쓰는 것을 파일 안에서 갈라 놓은 것이 이번 변경의 뼈대다.**
  - `common_criteria`를 `common_instructions`로 바꿨다. `criteria`의 모양이 유형마다 달라져 공통 문장을 거기에 붙일 수 없다. 붙일 곳은 `instructions`뿐이다. jev.md ⑥의 규칙도 함께 고쳤다.
  - `version`을 **1.1.0**으로 올렸다. 묻는 내용이 아니라 전송 형식이 바뀌었다.
  - **세 기능 경로를 실제로 불러 확인했다** (2026-10-21, ChatKHU Gateway). ① `page` 20건, ② `portal_list` 1건, ③ `selection` 19건 — **40건 전부 200, 8개 질문 모두 답을 받았다.**
  - 그 호출에서 문서에 없던 두 가지가 나와 README에 적었다.
    - **Score는 0~1이 아니라 0~(등급 수 − 1)이다.** `legend` 키가 `"0"`부터 시작하고 `score`는 등급 번호의 확률 가중평균이다. 등급 수가 다른 항목을 섞으려면 점수 합산 코드가 정규화해야 한다 (GE-15).
    - **Noul 응답은 `{"type": "noul", "noul": 0.63}` 하나뿐이다.** `confidence`도 `probabilities`도 오지 않는다. `undetermined_band`가 확신도 임계값 자리를 대신한다는 뜻이고, jev.md 2절이 이미 맞게 적고 있었다.
- **사람이 결정·수정한 것**:
  - 측정(GE-11)보다 스키마 교정을 먼저 하기로 했다. 틀린 형식으로는 측정할 것이 없다.
  - 판단 내용은 건드리지 말고 형식만 바꾸라고 범위를 정했다.
