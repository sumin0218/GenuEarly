# 04. 제작·개발

> 서식4의 **제작·개발** 단계다. 형식과 규칙은 [README.md](README.md)에 있다. 항목 하나가 결정 하나다. 최신 항목을 아래에 덧붙인다.

코드를 쓰면서 AI를 쓴 기록. 코딩 도구를 썼다면 **그것이 외부 도구이므로 사유를 적는다.**

## 이 단계에서 사람이 쥐고 있어야 할 것

- **PR 작성자는 모든 변경을 본인이 설명할 수 있어야 한다.** AI가 만든 코드도 마찬가지다.
- AI가 제안한 패키지가 **실제로 존재하는지** 확인했는가 (타이포스쿼팅, 환각 패키지).
- AI가 제안한 코드에 `innerHTML`, 원격 스크립트 로드, 과도한 권한이 섞여 있지 않은가. 학습 데이터에는 MV2 시절 코드가 훨씬 많다.
- AI 도구에 키나 `.env` 내용을 넣지 않았는가.

**AI 제안을 버린 기록을 반드시 남긴다.** 무엇을 왜 버렸는지가 우리가 한 판단이다.

### 확장 프로그램 빌드 도구 선정 (GE-9)

- **날짜**: 2026-10-14
- **AI 모델**: 코딩 도구 (Claude Code / Claude Opus 5)
- **외부 도구 사용 사유**: npm 레지스트리 배포 이력 조회와 공식 문서 교차 확인이 필요한 조사 작업이다. ChatKHU의 역할(판단 기준 설계, 사용자 노출 문구 작성)에 해당하지 않는다.
- **주요 프롬프트**: "Manifest V3 확장 프로그램 빌드 도구의 현황을 조사하고, WXT와 CRXJS를 우리 요구사항 기준으로 비교하라"
- **결과**: WXT 권고. 근거는 `createShadowRootUi`(Shadow DOM 주입)와 `wxt zip`(제출용 패키징)이 내장이라는 점. CRXJS는 `manifest.json`을 직접 관리해 권한 표와 1:1로 대응되는 장점이 있으나 위 둘을 직접 구현해야 한다.
- **사람이 결정·수정한 것**:
  - **AI가 제시한 근거 하나를 기각했다.** WXT 공식 비교 문서에 "CRXJS는 maintenance mode, 개발이 거의 없음"이라고 적혀 있어 그것을 선정 근거로 가져왔다. npm 배포 이력을 교차 확인시키니 **CRXJS는 v2.3.0(2025-12)부터 v3.0.0(2026-09-24)까지 활발히 배포 중**이었다. 공식 문서가 옛 정보였고, 해당 근거를 선정 사유에서 제외했다. 경쟁 도구에 대한 서술을 그 도구 제작자의 문서로 판단하지 않는다.
  - **언어 결정을 한 번 뒤집었다.** 처음에는 "팀이 JavaScript 경험이 있으니 순수 JS로 가자"고 정했다. 그러나 WXT 템플릿과 공식 예제가 전부 TypeScript임을 확인하고 **TypeScript 유지로 바꿨다.** `.js`로 내리면 공식 문서 예제를 그대로 쓸 수 없어 오히려 학습 비용이 커진다는 판단이다. 대신 타입 오류가 빌드를 막지 않게 두어 평범한 JS를 써도 되게 했다.
  - Plasmo는 npm 최종 배포가 2025-05-17로 17개월 정체되어 후보에서 제외했다.

### 권한 테스트가 콘텐츠 스크립트를 보지 못한다는 것을 리뷰에서 발견 (GE-9)

- **날짜**: 2026-10-16
- **AI 모델**: 코딩 도구 (Claude Code / Claude Opus 5) — 리뷰와 수정 양쪽
- **외부 도구 사용 사유**: 코드 리뷰와 수정 작업이다. ChatKHU의 역할에 해당하지 않는다.
- **주요 프롬프트**: (리뷰) "이 PR을 검토하라" / (수정) "지적을 확인하고 반영하라"
- **결과**: 바로 위에서 만든 테스트가 **`wxt.config.ts`의 `manifest` 객체만 읽고 있었다.** WXT에서 `content_scripts`는 `entrypoints/content.ts`의 `matches`로 생성되어 그 객체에 없다. 그래서 `matches`를 `<all_urls>`로 바꿔도 테스트 4개가 전부 통과했다. 마지막 검사(`content_scripts` 대상과 `host_permissions`의 불일치)는 늘 빈 배열을 보고 있어 아무것도 검사하지 않았다.
- **사람이 결정·수정한 것**:
  - **지적을 그대로 믿지 않고 재현부터 했다.** `matches`를 `<all_urls>`로 바꿔 4개가 통과하는 것을 직접 확인한 뒤 고쳤다.
  - **빌드된 `.output/chrome-mv3/manifest.json`을 읽도록** 바꿨다. `npm test`가 빌드를 먼저 돌린다. 같은 조작에서 이제 3건이 실패한다.
  - "검사가 헛돌지 않는지 확인하는 테스트"를 따로 넣었다. 빌드 결과에 `content_scripts`가 실제로 있는지 본다. 그게 깨지면 나머지 `matches` 검사가 아무것도 안 보고 있다는 뜻이다.
  - **같은 리뷰에서 네이버 기사 주소가 틀린 것도 드러났다.** 기사 본문은 `news.naver.com`이 아니라 `n.news.naver.com/article/…`에 있었다(첫 화면 기사 링크 415개 확인). 지금 설정으로는 기사에서 배지가 뜨지 않았다. 대상 목록을 `match-patterns.ts` 하나로 모아 `host_permissions`와 `matches`가 같은 값을 쓰게 했다.
  - **교훈**: "테스트를 만들었다"와 "테스트가 맞는 것을 보고 있다"는 다르다. 위반을 만들어 실패를 확인했는데도, **위반을 만든 위치가 테스트가 보는 곳이었기 때문에** 사각지대를 놓쳤다.

### Jev 호출 중계 구현 (GE-18)

- **날짜**: 2026-10-22
- **AI 모델**: **Jev** (`jev-1.13.0`, ChatKHU Gateway — 통합 테스트의 호출 대상) · 코딩 도구 (Claude Code / Claude Opus 5 — 구현과 테스트)
- **외부 도구 사용 사유**: 중계 서버가 실제로 Jev 에 닿는지는 모의로 알 수 없다. 통합 테스트에서 실제 호출을 보냈다.
- **주요 프롬프트**: "GE-18 중계 구현 바로 하자". 규약은 이미 [architecture.md](../architecture.md) 4절에 적혀 있어서, 그 문서를 구현으로 옮기는 작업이었다.
- **결과**: `apps/proxy/src/` 에 `schema.ts`(규약 검증)와 `jev.ts`(게이트웨이 호출)를 더하고 `index.ts` 의 `501` 자리를 채웠다. 테스트 37개.
  - **교차 검증이 핵심이다.** 항목 id 가 있는지만 보면 `headline_body` 그룹에 `clickbait_headline` 을 넣어 **제목 판단에 본문을 섞는** 요청이 통과한다. 항목·그룹·기능 세 짝이 맞는지까지 본다. 그 두 사례를 그대로 테스트로 박았다.
  - **실패를 오류로 올리지 않는다.** 429·타임아웃·5xx·보기 밖 응답은 전부 `200` 에 `{undetermined: true, reason}` 으로 돌아간다. ⚪ 는 실패가 아니라 결과다.
  - **Jira 에 적어 둔 완료 조건 하나를 일부러 다르게 구현했다.** "429 를 받으면 `retry-after` 를 지켜 한 번 재시도" 라고 적었는데, **실측 `retry-after` 가 19초였다.** 그만큼 기다리면 사용자는 20초 동안 빈 배지를 본다. 1.5초 안일 때만 다시 걸고 아니면 바로 ⚪ 로 돌리게 했다. **기다리는 것보다 모른다고 말하는 것이 낫다.**
  - **GE-31·GE-32 에서 잰 값이 그대로 코드가 됐다.** Score 가 0~(등급 수 − 1) 이라는 것이 응답 검증 조건이 되고, Noul 에 `confidence` 가 없다는 것이 그 유형의 검사 모양을 정했다. 게이트웨이가 늘 `jev-latest` 로 정규화한다는 것 때문에 모델 불일치 경고를 **격리 수명당 한 번만** 남기게 했다 — 매 요청 경고하면 로그가 쓸모없어진다.
  - **실제 게이트웨이에 붙이는 테스트를 따로 뒀다** (`tests/integration.test.ts`). 키가 없으면 건너뛰므로 CI 에서는 돌지 않는다. 다섯 경로(① 제목+본문 / ① 제목만 / ① 문장 / ② 목록 / ③ 선택) 전부 실제로 답을 받는 것을 확인했다.
- **사람이 결정·수정한 것**:
  - 구현을 **별도 PR** 로 올리게 했다.
- **왜 통합 테스트를 넣었나**: GE-31 에서 질문 세트 전체가 `400` 으로 돌아온 원인이 **아무도 한 번도 불러 보지 않은 것**이었다. 모의 테스트는 우리가 상상한 게이트웨이와만 맞춰 본다. 같은 일이 중계 서버에서 반복되지 않게 실제 호출을 선택 실행으로 남겼다.

### 중계 구현 PR 리뷰 반영 (GE-18)

- **날짜**: 2026-10-22
- **AI 모델**: 코딩 도구 (Claude Code / Claude Opus 5) — 리뷰와 반영 · **Jev** (반영 후 실제 호출 재확인)
- **외부 도구 사용 사유**: 위 항목과 같다.
- **주요 프롬프트**: PR #12 에 달린 리뷰(P2 2건, P4 2건)를 확인하고 반영하게 했다.
- **결과**: 4건 모두 반영했다. **P2 하나는 받아들이기 전에 재현부터 했다.**
  - **필드를 빼면 교차 검증을 우회할 수 있었다.** `{group: "headline_body", items: ["source_citation"], state: {headline: "…"}}` 를 보내면 그룹·기능의 짝은 맞으므로 통과한다. 고치기 전에 실제로 보내 보니 **`200` 이었고 `headline` 만 담긴 요청이 Jev 로 나갔다.** PR 본문에 "막았다" 고 적은 바로 그 사례가 다른 길로 통과하고 있었다. `request_groups.*.required` 를 기능별로 두고 검사를 더했다. ③ 선택 텍스트는 같은 그룹을 `body` 만으로 쓰므로 기능마다 다르게 둔다.
  - **`in` 이 프로토타입까지 본다.** `'constructor' in {}` 는 참이다. 보기 밖의 답을 거르는 검사인데 `constructor`·`toString` 같은 값이 통과했다. 직접 확인하고 `Object.hasOwn` 으로 바꿨다. 그룹 조회와 항목의 기능 조회도 같이 바꿨다.
  - **이 PR 부터 키가 실제로 쓰인다.** 머지 자체는 안전하다(배포 워크플로가 없어 자동 배포되지 않는다). 다만 배포하면 Origin 을 위조해 누구나 우리 키를 쓸 수 있다. README 배포 절에 **"GE-20 전에는 `wrangler deploy` 하지 않는다"** 를 명시했다.
  - **`answers` 의 키가 항목 id 가 아니라 질문 id 라는 것이 규약 문서에 없었다.** 확장 프로그램이 `answers[항목id]` 로 찾으면 `unverifiable_claim` 만 늘 ⚪ 가 된다. [architecture.md](../architecture.md) 4절과 proxy README 에 적었다 (GE-22 에서 쓴다).
  - 테스트 37개 → **44개.** 늘어난 7개가 전부 위 두 P2·P4 를 막는 것이다.
- **사람이 결정·수정한 것**:
  - 세 PR 의 리뷰를 모두 반영하고 머지하기로 했다.
- **교훈**: PR 본문에 "이것을 막았다" 고 쓴 사례가 **다른 입력으로는 안 막히고 있었다.** 막았다는 주장은 그 주장대로 한 번 때려 봐야 한다.

### 크레딧 잔액 감시 (GE-20)

  - 문장 분리기를 옮긴 뒤 **원본과 기사 84건에서 결과가 한 글자도 다르지 않은 것을 확인**하고 넘어갔다.
- **실제로 돌려 보고서야 드러난 것 넷.** 모의 테스트로는 하나도 안 잡혔다.
  - **`User-Agent` 가 없으면 게이트웨이가 403 을 준다.** API 가 아니라 앞단 WAF 가 막는 것이라 본문이 HTML 로 온다. **workerd 는 UA 를 기본으로 붙이지 않는다.** 모의도, node 에서 도는 통합 테스트도 이것을 못 잡는다 — node 는 UA 를 붙이기 때문이다. **배포했으면 모든 판단이 ⚪ 가 됐을 것이다.**
  - **`textContent` 가 `<br>` 과 단락 경계를 없는 것으로 본다.** "…권고했다.과학기술정보통신부는…" 처럼 마침표 뒤에 공백이 없어 **문장 분리가 통째로 실패했다**(32문장짜리가 15문장으로 뭉침). 줄을 나누는 요소 자리에 개행을 심어 고쳤다.
  - **바이라인 모양이 생각보다 다양하다.** `[서울=뉴시스]조수원 신유림 기자, 임다빈 수습기자 =` 처럼 기자가 여럿이고 "수습기자" 가 섞인다. 정규식을 넓히고 대괄호 안에 들어간 형태도 함께 처리했다.
  - **부제를 본문 첫머리에 `<br>` 로 나열하는 매체가 있다.** 바이라인이 없어 안 걷히고, 부제 세 줄과 첫 문장이 한 덩어리가 되어 그대로 판단 대상이 됐다. 종결부호로 끝나지 않는 짧은 앞줄을 버리도록 했다.
  - **`String.raw` 를 쓰지 않으면 템플릿 리터럴이 `\s` 를 `s` 로 죽인다.** 정규식이 조용히 다른 뜻이 된다. 이 저장소에서 같은 함정을 여러 번 밟았다.
- **사람이 결정·수정한 것**:
  - 프로토타입을 먼저 만들자고 했다. **그 결정이 위 넷을 전부 드러냈다** — 설계만 더 했으면 배포 후에 알았을 것들이다.
